The monitoring API provides account hashrate, worker status, share statistics, fees, estimated earnings, and confirmed payout-output history for automatic monitoring systems. Use the HTTPS base URL https://api.dmnd.work/api/v1. The dashboard's unversioned /api routes provide compatibility for existing watcher workflows; their earnings-history defaults differ as described below.

Authentication and access

Create a monitoring token in the dashboard's API Keys page. Select the exact account to monitor and only the required scopes. The signed-in owner can retrieve available secrets and open or copy watcher links from this page. Store the token in your monitoring system's secret store.

Send the token in the HTTP header Authorization: Bearer <token>. Query-string credentials are rejected by /api/v1. Mining tokens and FPPS credentials are not monitoring credentials. Only active dedicated monitoring-key records authenticate, including preserved historical keys. Programmatic clients should send no session cookies. When both a bearer token and a dashboard session are supplied, the bearer token determines the account and scopes.

Tokens have no expiration by default; an owner can choose an explicit future expiry. Check the listed expiry for each key, since existing keys retain their stored dates. Each target account may have at most 100 active tokens. Revoking a token prevents authentication on subsequent requests; requests already authenticated may finish. If a key expires or must be rotated, create a replacement, update the monitoring secret, check a successful read, and then revoke the old key.

Existing unversioned monitoring GET URLs may use a single token query parameter for compatibility. Do not add query credentials to new integrations: URLs can leak through logs and link previews. An Authorization header combined with a query credential, duplicate query credentials, or a query credential on any /api/v1 endpoint is rejected.

An account token can read that account and its directly owned subaccounts, subject to its scopes. A token created for a specific subaccount cannot read the master or sibling subaccounts. Account IDs are decimal strings, including negative values; preserve them exactly and do not parse them as JavaScript numbers.

ScopeData exposed
hashrate_readCurrent and historical PPLNS, FPPS, and total hashrate
workers_readWorker names, online status, hashrates, and accepted/rejected counters
rejects_readAccount share counter deltas for a requested time window
fees_readPool and broker fee rates
earnings_readFPPS generated BTC, PPLNS projected amounts, and recorded-address payout history

These are read permissions, but the data is private: worker names can identify sites and earnings can reveal business activity. A watcher link grants access to anyone who possesses it. Treat the entire link as a secret; do not include it in support tickets or third-party link previews.

Example: one monitoring read

Provision DEMAND_MONITORING_TOKEN through your secret manager. This Python standard-library example makes one request, sets a timeout, and prints the decoded data without logging the token:

Python
import json
import os
import urllib.request

request = urllib.request.Request(
    "https://api.dmnd.work/api/v1/user/hashrate",
    headers={
        "Authorization": "Bearer " + os.environ["DEMAND_MONITORING_TOKEN"],
        "Accept": "application/json",
    },
)
with urllib.request.urlopen(request, timeout=20) as response:
    snapshot = json.load(response)
print(snapshot)

The key needs hashrate_read. A scheduled collector must also handle HTTP errors and apply the polling/backoff rules below; this one-shot example does not retry.

Hashrate and freshness

/user/hashrate returns raw hashes per second (H/s):

JSON
{
  "account_id": "9223372036854775807",
  "observed_at": "2026-09-08T10:00:00Z",
  "pplns_hashrate": 150000000000000,
  "fpps_hashrate": 50000000000000,
  "total_hashrate": 200000000000000
}

The subaccount hashrate routes return each rate as a value/unit object, rounded to two decimal places. The unit is TH/s or PH/s. For example:

JSON
{
  "account_id": "1234567890123456789",
  "observed_at": "2026-09-08T10:00:00Z",
  "pplns_hashrate": {"value": 150.0, "unit": "TH/s"},
  "fpps_hashrate": {"value": 50.0, "unit": "TH/s"},
  "total_hashrate": {"value": 200.0, "unit": "TH/s"}
}

Snapshots are normally written every two minutes from fresh worker telemetry. A worker is online while its latest telemetry is less than ten minutes old. These values are not instantaneous miner measurements. Use observed_at to detect stale collection separately from low hashrate. When no snapshot exists, observed_at is null and all hashrates are zero.

Historical endpoints return arrays of snapshots in ascending observed_at order. Supply from and to as RFC3339 timestamps or YYYY-MM-DD dates. A date-only from means 00:00:00 UTC; a date-only to means 23:59:59 UTC. Omitted bounds default to the last 24 hours. The maximum span is seven days and each response is bounded to 6,000 points. The service retains approximately 100 days.

To backfill longer periods, request successive windows no larger than seven days and deduplicate shared boundary timestamps. Freeze the range before the first request so its end does not move between pages. An empty array means there are no snapshots in that window.

Workers, counters, and fees

Worker endpoints accept limit (default 200, maximum 1,000) and an opaque cursor. Responses have the shape {"workers": [...], "next_cursor": "..."}. Pass next_cursor unchanged to the next request; null marks the last page. The roster can change while pages are fetched.

Each worker contains name, is_connected, and connected_at (Unix milliseconds or null). hashrate and fpps_hashrate are raw H/s, even on subaccount worker routes. The PPLNS counters are total_shares and rejected_shares; FPPS equivalents begin with fpps_. Missing telemetry for one payment mode is represented by null. Counter resets and disconnected miners can affect deltas.

Share-statistics endpoints accept hours, default 24 and maximum 168. Responses contain window_hours, pplns_accepted, pplns_rejected, fpps_accepted, fpps_rejected, accepted, and rejected. Calculate a rejection ratio as rejected / (accepted + rejected) when the denominator is nonzero. Counters are telemetry-derived; they are not a count of immutable raw share records.

Fee endpoints return pool_fee and broker_fee as fractions: 0.02 means 2%.

Earnings windows

Versioned generated-BTC endpoints return daily arrays in descending entry_day order. Optional date selects one UTC day. Otherwise, before is the inclusive final UTC day of a page (default today) and limit is the number of calendar days (default 30, maximum 100). Use the preceding calendar window for older data; missing mining days are omitted and are not a signal that older data is unavailable. date cannot be combined with before or limit.

The unversioned dashboard earnings routes return complete available history when these parameters are omitted, so dashboard history and exports do not require pagination. Automation using /api/v1 retains the bounded defaults above.

Every row contains:

  • entry_day: YYYY-MM-DD in UTC;
  • fpps_btc_generated: generated FPPS BTC;
  • pplns_btc_generated: cached future PPLNS projected BTC attributed to that work day;
  • btc_generated: the sum of those two values;
  • hashrate: the FPPS-derived daily rate in H/s, or zero for a projection-only day;
  • pplns_hashrate: recorded accepted-share PPLNS work in raw H/s, or null when unavailable.

pplns_hashrate groups accepted shares by their database-recorded UTC day, not miner-supplied ntime. Ingestion delays can move work into a later recorded day. Completed days use sum(difficulty) * 2^32 / 86400; today uses elapsed whole seconds since UTC midnight. Rates are rounded to two decimal places. They do not use worker telemetry or the difficulty retained in the moving PPLNS reward window. The existing FPPS hashrate keeps its separate meaning.

PPLNS rate coverage is limited to today and the previous 99 UTC days, and starts no earlier than the first complete UTC day after the database's explicit-UTC share-timestamp migration. Earlier timestamps cannot prove complete correctly dated work. Older earnings rows remain present with pplns_hashrate: null; raw work alone does not add earnings rows. A successfully read covered day with no recorded work has pplns_hashrate: 0. Unavailable history is never reported as zero.

The supplemental rate has a 60-second cache, a maximum of 128 cached account/range combinations, one concurrent refresh per server, and three refresh attempts per target account per minute. Existing account ownership is resolved before cache lookup. A refresh has a five-second SQL deadline. Busy refreshes, exhausted refresh budgets, source errors, and invalid work values produce null without failing or changing the earnings response; failed refreshes are cached for 60 seconds. Large account histories can exceed the deadline. For current monitoring, request ?date=YYYY-MM-DD for today's UTC date every two to five minutes. For backfills, use smaller date windows and wait at least 60 seconds before retrying unavailable rates. Do not replace null with zero in your client.

PPLNS projections can change and exclude amounts already earned from found blocks. Consequently, btc_generated is not a paid balance, payout guarantee, or settled accounting record. The FPPS accumulator normally runs every five minutes. A requested single day with no earnings returns one zero-earnings row, consistently for account and subaccount routes; its supplemental PPLNS rate follows the independent recorded-work coverage rules above.

Confirmed payout history

GET /user/payouts returns confirmed FPPS/PPLNS transaction outputs associated with the account's recorded Bitcoin addresses, including inactive addresses and directly owned subaccounts. GET /user/sub_account/{id}/payouts restricts the result to that exact authorized account. Both require earnings_read; the API never initiates payments or changes payout addresses.

This is address-associated transaction history, not an account ownership ledger. Address records have no effective ownership dates, so even an unshared recorded address does not prove who owned it at the time of a historical payment. If any address is also recorded against an account outside the requested set, the complete request returns HTTP 409 with code payouts-ambiguous-address; it does not guess attribution or silently omit that address. An aggregate request may include an address shared entirely within its requested account set, but the corresponding exact-account request is ambiguous when another recorded owner lies outside it.

Funding inputs must match the configured FPPS/PPLNS sources or the historical FPPS source bc1qwk7rplr3ztrsvlcxujnxdvp77atpqawlh94wgw. Only outputs to authorized recorded recipient addresses are returned. Unrelated recipients, transfers back to funding addresses, unrelated deposits and unconfirmed transactions are excluded. Each (txid, output_index) appears once, including when addresses are shared within an aggregate or several funding inputs match.

Parameters:

  • from, to: inclusive UTC dates (YYYY-MM-DD), with no future dates. to defaults to today; from defaults to 29 days before to. The maximum window is 30 calendar days.
  • limit: outputs per page, default 100 and maximum 100, minimum 1.
  • cursor: the previous response's next_cursor, unchanged. Keep the same explicit dates and target account while traversing a window. A null cursor marks the final page.

For example, use /user/payouts?from=2026-09-01&to=2026-09-09&limit=100 with the same Bearer header shown above. Its response has this shape:

JSON
{
  "payouts": [
    {
      "txid": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
      "output_index": 2,
      "kind": "fpps",
      "address": "<recorded Bitcoin address>",
      "amount_sats": 125000,
      "confirmed_at": 1788912000
    }
  ],
  "next_cursor": null,
  "as_of": 1788912300,
  "from": "2026-09-01",
  "to": "2026-09-09"
}

amount_sats is an integer number of satoshis, never a floating-point BTC amount. output_index is the zero-based transaction output index; kind is fpps or pplns. confirmed_at is the upstream block timestamp in Unix seconds, not the payment request time. as_of is the server's snapshot retrieval time in Unix seconds. Rows are ordered descending by confirmation timestamp, then transaction ID and output index. An empty page means no matching confirmed outputs in a completely retrieved window, or no recorded recipient addresses.

Chain snapshots are cached for at most 60 seconds, with at most four windows per server process. One provider fill may run at a time, and at most six uncached windows may be requested per fixed 60-second interval across all customers on that process. These limits are additional to normal monitoring budgets; HTTP 429 includes Retry-After. Poll payouts every few minutes, reuse pages, and backfill one fixed window at a time. Allow a client timeout long enough for a 20-second provider deadline plus authentication/database work.

Provider reads are bounded to 20 pages per funding source, 1 MiB per upstream response and 50,000 outputs per window. A historical date window may exceed the scan-depth limit even when it contains few payouts, because the upstream index is walked from its newest transaction. Missing configuration, provider errors, timeouts, incomplete scans or inconsistent data return HTTP 503, never a successful empty or truncated history. Respect its Retry-After header.

Confirmed transactions can be reorganized. After cache expiry the service fetches fresh chain history; it does not serve stale results when refresh fails. A changed funding snapshot, requested window, target, or recorded recipient set invalidates the cursor with HTTP 409 and code payouts-cursor-changed. A funding-snapshot change may affect another recipient rather than your account. Restart pagination without a cursor, using the same fixed window, and reconcile collected outpoints against the replacement snapshot instead of assuming confirmations are irreversible.

Polling, errors, and compatibility

Polling current statistics every two to five minutes is appropriate for the snapshot cadence. Avoid re-fetching all history on every poll. Cache the collected data in your own monitoring store, stagger accounts, bound concurrent requests, and configure connection and request timeouts.

The service allows 240 requests per token and 600 requests per token account in each fixed 60-second window; multiple tokens for the same account share the account budget. There is also a 1,200-request client-IP budget across protected API paths. These limits are per server process, not a guaranteed cluster-wide allowance; obey every 429 even when your own counter is lower. Additional edge protection or temporary capacity limits may also reject traffic.

Responses containing account data use Cache-Control: private, no-store. Do not record bearer headers, API secrets, watcher links, or credential-listing/creation responses in request logs, traces, or alerts. HTTP 429 includes Retry-After in seconds. Wait at least that long and add random jitter. Retry transient server errors with bounded exponential backoff; do not keep retrying 400, 401, or 403.
